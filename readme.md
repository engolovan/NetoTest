# Подсистема приоритетного управления видеонаблюдением (ППУВ)

## 1. Общая концепция

### 1.1. Бизнес-контекст

* Подсистема приоритетного управления видеонаблюдением (ППУВ) реализуется в **федеративной** архитектуре: **отдельная платформа СРВИ** (контур уполномоченного ведомства) и **одна или несколько региональных платформ**.
* <span style="color:blue;">Даже минимальная схема из двух платформ считается федерацией. Реализация не должна строиться как временная "нефедеративная" полумера с последующим переносом: уже в первой поставке нужно закладывать взаимодействие независимых платформ через явные межсистемные интерфейсы.</span>
* Ключевое требование:
  * региональные площадки **не сводятся в единую сеть**;
  * уполномоченному ведомству предоставляется **приоритетный бесшовный доступ** к системам видеонаблюдения.

### 1.2. Принципы архитектуры

* **Две (и более) независимые платформы**: у СРВИ и региональной системы — **свой фронтенд и свой бэкенд**. Пользователь, залогиненный в одной системе, **не выполняет операции** в другой напрямую.
* <span style="color:blue;">Пользователь СРВИ никогда не заходит в региональную платформу под пользовательским аккаунтом. Все действия выполняются из UI СРВИ, а в регион уходят только доверенные S2S-команды.</span>
* **Одинаковый состав платформ**. СРВИ — это **не урезанная** копия; по набору сервисов платформы эквивалентны. Отличие будет в сценариях использования.

  Это также означает, что на СРВИ могут быть свои камеры, аналитики, уведомления и т.п., которые доступны только со стороны платформы СРВИ.
* **СРВИ — точка управления ППУВ**. Блокировки, перехват, журнал блокировок, аудит операций ППУВ будут находиться **на стороне СРВИ**. На региональной платформе **нет** операторского ППУВ-функционала (супер-оператор, перехват чужих блокировок и т.п.). Технически элементы ППУВ могут быть включены, но должны пресекаться на управленческом уровне.
* <span style="color:blue;">Главенство СРВИ проявляется в спорных ситуациях ППУВ: блокировка камеры, блокировка архива, резервирование, выборочная запись и перехват PTZ. В остальных доменных сценариях региональная система продолжает жить как самостоятельная платформа.</span>
* **Интеграция через RSM, не через EM**. Взаимодействие между платформами — **отдельные S2S-интеграции** (расширенный RSM, прокси-команды), а не "склейка" внутренних сервисов одной инсталляции.
* **Масштабирование на N регионов**. На текущий момент может быть только одна региональная система, но закладываем возможность нескольких.

  При включении новых платформ возможен вариант как добавления новой региональной структуры в текущую систему, так и разворачивания новой связки СРВИ и региональной платформы.
* **Признак происхождения камеры**. В UI и в данных обязательно различать: локальные камеры СРВИ, камеры региональной системы A, камеры региональной системы B и т.д.
* <span style="color:blue;">Даже если в первой поставке подключен один регион, признак источника, `externalId` камеры и идентификатор региональной инсталляции обязательны. Это критерий приемки бэкенд-архитектуры, а не опциональная UI-метка.</span>
* **Live-отображение**:
  * для гражданского пользователя должно быть всё максимально скрыто, или казаться, что камера не работает или не пишется архив;
  * для пользователя СРВИ должно быть визуально понятно, откуда получены камеры, и должны быть видны заблокированные фрагменты на таймлайне.
* **События аналитик и нотификации** просматриваются для каждой платформы отдельно. Пользователь СРВИ не видит аналитики на региональной платформе. Пользователь СРВИ видит только события по локальным камерам СРВИ.
* <span style="color:blue;">При блокировке архива или камеры региональная платформа должна скрывать от гражданских пользователей не только архивные сегменты, но и события аналитик/нотификации за соответствующий интервал. Для СРВИ эти региональные события всё равно не агрегируются.</span>
* **Аудит.** Региональный пользователь не видит, что сделал оператор СРВИ, данные никак **не отображаются в аудите** региональной платформы. Но в аудите СРВИ все действия сохраняются. Пользователь СРВИ **не видит аудит** на региональной платформе.
* **Журнал блокировок** отображается только на платформе СРВИ, с учётом всех необходимых функций (сортировки, фильтрации, разблокировки камеры).
* Одна лицензия по работе с ППУВ распространяется на обе платформы. Вопрос доступов решается через управленческое воздействие.
* Конфликты решаются **по каждой камере отдельно**, а не "вся зона целиком чья-то или ничья".

### 1.3. Типы камер и данных

```text
┌─────────────────────────────────────┐     S2S (RSM)      ┌──────────────────────────────────┐
│           Платформа СРВИ            │ ◄──────────────► │   Региональная платформа (×N)    │
│  • локальные камеры (свой контур)   │                  │  • муниципальные камеры          │
│  • проекции камер из регионов       │                  │  • медиастримеры + Nimble        │
│  • медиастримеры для блокировок /   │                  │  • приём команд блокировки       │
│    резервирования                   │                  │    от СРВИ                       │
│  • RFM для долговременных копий     │                  │  • логическое скрытие архива     │
└─────────────────────────────────────┘                  └──────────────────────────────────┘
```

<span style="color:blue;">Проекции региональных камер должны быть доступны в каталоге СРВИ заранее или создаваться управляемо при первом действии. В обоих вариантах СРВИ хранит собственный `resourceId`, внешний `externalId` камеры региона и `regionalInstallationId`.</span>

### 1.4. Операции и сущности ППУВ

* **Важно!**
  * Все операции ППУВ инициируются на платформе СРВИ.
  * Сохранённые элементы архива в RFM должны отображаться на таймлайне камеры.
  * <span style="color:blue;">Оператор СРВИ смотрит федеративную камеру через камеру/плеер СРВИ. Плеер должен уметь собирать единый таймлайн из регионального медиастримера, стримера СРВИ и RFM, не заставляя пользователя переходить в региональную систему.</span>

#### Блокировка камеры (спецрежим)

* Спецпользователь **скрывает реальную картину** с камеры от гражданских на время операции: вместо live — нерабочий поток (для одиночной камеры) или заглушка/подмена (для раскладки); архив за период блокировки для них недоступен, так же как события. Для пользователя ППУВ поток и запись остаются реальными. Снимается по **TTL** или вручную.
* Блокировка камеры затрагивает блокировку архива.
* <span style="color:blue;">На региональной платформе при блокировке применяется логическое скрытие для гражданского контура; данные региона не удаляются. Одновременно СРВИ включает собственную запись/копию нужного потока на своём медиастримере для периода блокировки.</span>
* <span style="color:blue;">После завершения блокировки заблокированный фрагмент должен быть зафиксирован в RFM СРВИ для долговременного хранения. Политика хранения настраиваемая; Nimble/медиастример не считается надёжным долговременным хранилищем, так как архив может быть очищен штатной ретенцией.</span>

#### Перехват PTZ (PTZ preemption)

* Спецпользователь ППУВ **принудительно забирает управление** поворотной камерой у текущего пользователя за счёт более высокого приоритета. Live и архив **не отключаются**; предыдущий оператор получает уведомление.

#### <span style="color:dimgray;">*Блокировка положения камеры (PTZ-lock) — будущая итерация*</span>

* <span style="color:dimgray;">*Оператор* ***закрепляет за собой управление*** *PTZ на камеру или группу. Пока блокировка активна, другие не могут поворачивать камеру; просмотр live и архива для всех остаётся доступным.*</span>

#### Блокировка архива (Archive-lock) и изъятие

* Возможны 2 варианта блокировки архива:
  * **Логическая блокировка:** оператор закрывает доступ к записям за выбранный период. На таймлайне у гражданских — "дыра"; live не затрагивается. Блок **не снимается автоматически**. Скрытие **обратимо** при снятии lock.
  * **Физическая блокировка:** оператор **накладывает логическую блокировку** на фрагмент гражданского контура и **копирует фрагмент архива** с регионального Nimble/медиастримера в RFM СРВИ.

    Физическая блокировка выполняется при блокировке камеры, а также может быть выбрана при блокировке выделенного фрагмента.

    Блок снимается стандартным образом.
* <span style="color:blue;">Для просмотра полного архива федеративной камеры СРВИ не обязан предварительно дублировать весь архив. Обычные интервалы могут читаться по подписанной внешней ссылке/прокси с регионального медиастримера, а заблокированные, зарезервированные и изъятые интервалы — из источников СРВИ/RFM.</span>

#### Резервирование архива

* Оператор **заранее** подключает федеративную камеру к **параллельной записи** на медиастример СРВИ, не скрывая поток от гражданских. Это необходимо, чтобы при отказе региональной площадки сохранились live и архив в контуре СРВИ.
* <span style="color:blue;">Резервирование может быть срочным или бессрочным до ручного снятия. В отличие от блокировки камеры, оно не мешает гражданскому контуру и не должно скрывать live/архив/события у региона.</span>
* <span style="color:blue;">Резервирование означает подключение потока к контуру СРВИ, а не только последующую выгрузку файла: СРВИ должен иметь собственную запись на период резервирования.</span>

#### Выборочная запись архива

* Оператор **сохраняет копию** уже существующего исторического фрагмента (файл из Nimble/медиастримера региона) в RFM СРВИ.
* <span style="color:blue;">Оператор выделяет интервал на таймлайне СРВИ; система получает файл из регионального архива через S2S/служебный API и сохраняет его в RFM без удаления оригинала и без блокировки live.</span>

#### Взаимовлияние сущностей

| Сущность | Спецрежим | <span style="color:dimgray;">*PTZ-lock (будущее)*</span> | Перехват PTZ | Archive-lock |
| --- | --- | --- | --- | --- |
| Блокировка камеры | — | Затрагивает | Затрагивает | Затрагивает (авто) |
| <span style="color:dimgray;">*PTZ-lock*</span> | Не влияет | — | Затрагивает | Не влияет |
| Перехват PTZ | Не влияет | Затрагивает | — | Не влияет |
| Archive-lock | Не влияет | <span style="color:dimgray;">Не влияет</span> | Не влияет | — |
| <span style="color:blue;">Резервирование архива</span> | <span style="color:blue;">Не скрывает, но может совпадать по камере</span> | <span style="color:blue;">Не влияет</span> | <span style="color:blue;">Не влияет</span> | <span style="color:blue;">Не влияет</span> |

### 1.5. Пользователи

* В федеративной схеме роли привязаны к платформе, на которой пользователь аутентифицирован. ППУВ-операции доступны только на СРВИ; региональная платформа не предоставляет операторский ППУВ-функционал (супер-оператор, перехват чужих блокировок и т.п.).
* Возможные пользователи:
  * **Спецпользователь (ППУВ) — контур СРВИ:** наивысший приоритет в рамках СРВИ. Перехват PTZ, блокировка камер и архива (в т.ч. проекций регионов), скрытие действий от регионального аудита, работа с изъятым архивом в RFM, журнал блокировок. Видит события аналитики и нотификации только по локальным камерам СРВИ; аналитика региональных платформ для него недоступна.
  * **Гражданский оператор — региональная платформа:** базовый приоритет. Управляет муниципальными камерами, пока RSM не применил ограничение со стороны СРВИ. При блокировке/перехвате теряет доступ согласно §1.6; **не видит** в аудите действий оператора СРВИ.
  * **Гражданский оператор — СРВИ (локальные камеры):** штатная работа с камерами контура СРВИ без ППУВ-приоритета; при конфликте с ППУВ — те же правила вытеснения.
  * **Системный администратор — на любой из платформ:** настраивает уровни доступа в Resource Management **своей** платформы, но **не получает** оперативного приоритета над ППУВ в реальном времени.

**Особенности:**

* Для пользователей с **одинаковым приоритетом** — право первого (first-come-first-served).
* Снять блокировку может **только владелец** или пользователь со спецправом перехвата/администрирования ППУВ на СРВИ (`admin:ppuv` / `ppuv:admin`).
* <span style="color:dimgray;">*На будущее: числовые приоритеты для промежуточных ролей (30 / 50 / 70) с попарным сравнением при конфликтах.*</span>

### 1.7. Технические нюансы

* RSM — сервис, хранящий состояние блокировок (что и кем занято) и координирующий сквозные операции. При нажатии "заблокировать камеру" он проверяет права, по таблице сопоставления находит нужный региональный контур, отправляет команду региональному RSM, запускает запись архива на стример СРВИ и фиксирует событие в журнале. Всё это скрыто от оператора за одним действием, а сам RSM также обслуживает импорт камер, блокировку архива и перехват PTZ.
* В каталоге СРВИ камеры из разных регионов выглядят одинаково для оператора, но внутри системы это разные сущности: при импорте создаётся собственная запись (`resourceId`), к которой привязываются `externalId` камеры в регионе и идентификатор региональной инсталляции. Эта таблица сопоставления нужна RSM, чтобы понимать, в какой именно региональный контур отправлять команду блокировки.
* Региональная система остаётся закрытой для обычных пользователей, но предоставляет контролируемый server-to-server API — служебный вход исключительно для доверенного контура СРВИ, через который RSM отправляет команды блокировки, разблокировки и работы с архивом. Защита типовая для межсистемной интеграции: ключи, client id, проверка подписи и разграничение по приоритетам.
* Пока камера не в спецрежиме, архив пишется на региональных медиастримерах. При блокировке гражданским показывается заглушка/подмена, их архив за этот период закрыт, а запись нужного интервала ведётся в контуре СРВИ.
* <span style="color:blue;">Для просмотра незаблокированных исторических интервалов допустим сценарий, где СРВИ получает от регионального медиастримера подписанную внешнюю ссылку или проксируемый DVR/HLS-ресурс. Это решает просмотр без массового дублирования всех архивов.</span>
* <span style="color:blue;">Для заблокированных, зарезервированных и изъятых фрагментов источник данных для плеера СРВИ — медиастример СРВИ и/или RFM. На уровне фронта это должен выглядеть как единый таймлайн камеры, даже если физически куски лежат в разных местах.</span>
* RFM в контуре СРВИ нужен, когда оператор не просто скрывает архив на время, а забирает насовсем или сохраняет копию прошлого фрагмента.
* Нужно учесть, что Nimble не умеет "перелить" архив целиком с сервера на сервер как единый поток — только выгрузить файл. RFM как раз место, куда этот файл кладут надолго.
* <span style="color:blue;">После окончания блокировки камеры нужен системный триггер/процесс, который сохраняет соответствующий фрагмент в RFM. Иначе фрагмент может быть потерян после очистки архива медиастримера.</span>
* <span style="color:blue;">Автоматическая замена заблокированной камеры случайной онлайн-камерой в раскладке является требованием ТЗ, но должна поставляться под feature flag и по умолчанию быть выключенной. Статичный пресет/картинка не закрывает это требование как полная замена, но может использоваться для одиночного просмотра "камера не работает".</span>

### 1.8. Чек-лист приемки федеративной части

<span style="color:blue;">Этот раздел добавлен по итогам встречи как компактный список решений, которые нужно видеть при разработке и приемке.</span>

* <span style="color:blue;">Камеры региона видны в СРВИ как проекции с собственным `resourceId`, `externalId` и `regionalInstallationId`.</span>
* <span style="color:blue;">Все ППУВ-действия над региональными камерами запускаются из UI СРВИ; пользователь СРВИ не логинится в региональную платформу.</span>
* <span style="color:blue;">Блокировка камеры на регионе скрывает live, архив, события и нотификации от гражданских пользователей региона, но не пишет следы операции в гражданский аудит региона.</span>
* <span style="color:blue;">Период блокировки доступен оператору СРВИ на таймлайне камеры и сохраняется в RFM для долговременного просмотра.</span>
* <span style="color:blue;">Полный таймлайн федеративной камеры в СРВИ может состоять из региональных DVR/HLS-ссылок, собственного архива СРВИ и RFM-фрагментов.</span>
* <span style="color:blue;">Резервирование архива работает без скрытия гражданского live/архива и может быть бессрочным до ручного снятия.</span>
* <span style="color:blue;">Выборочная запись исторического интервала сохраняет файл в RFM без удаления оригинала с регионального медиастримера.</span>
* <span style="color:blue;">Для раскладок случайная подмена заблокированной камеры реализуется как отключаемая feature flag.</span>

## 2. Бизнес-требования (User Stories)

### 2.1. Блокировки и управление ресурсами

* **US.PPUV.1.1.** Как пользователь ППУВ на платформе СРВИ, я хочу включать режим блокировки/спецоперации на камере через тумблер с выбором периода блокировки и повторным нажатием для снятия, с отображением состояния на иконке камеры, чтобы скрывать реальную картину от гражданских пользователей, оставаясь с доступом к настоящему потоку и архиву.
* **US.PPUV.1.2.** Как пользователь ППУВ на платформе СРВИ, я хочу видеть при одиночном просмотре камеры на карте, в списке и в галерее иконку блокировки и время до окончания блокировки камеры, чтобы понимать, какие камеры заняты и когда освободятся.
* **US.PPUV.1.3.** Как гражданский оператор региональной платформы, я хочу, чтобы камера в режиме спецоперации незаметно исчезала из моей раскладки и заменялась другой, а в одиночном просмотре показывала "неработающую" камеру, чтобы не привлекать внимание к проводимой операции.

  <span style="color:blue;">Важно: случайная онлайн-подмена в раскладке должна быть реализована как feature flag и по умолчанию отключена.</span>
* **US.PPUV.1.4.** Как пользователь ППУВ на платформе СРВИ, я хочу перехватывать управление поворотной камерой (в том числе проекцией региональной площадки) с блокировкой других пользователей, чтобы вести слежение за объектом без помех.
* **US.PPUV.1.5.** Как пользователь ППУВ на платформе СРВИ, я хочу выделить на карте область (лассо) и заблокировать камеры внутри неё (не более 50 за операцию), выбрав длительность из предложенных вариантов, чтобы оперативно закрепить зону наблюдения; при пересечении с областью другого пользователя система должна однозначно определить владельца каждой камеры и уведомить меня о частичном успехе или отказе.
* **US.PPUV.1.6.** Как пользователь ППУВ на платформе СРВИ, я хочу выделить ранее заблокированную мной область на карте и снять блокировки со всех своих камер в ней, чтобы освободить зону для других пользователей.
* **US.PPUV.1.7.** Как гражданский оператор региональной платформы, я хочу получать явное уведомление и отключение PTZ-управления при перехвате камеры оператором ППУВ с платформы СРВИ, чтобы не продолжать бесполезные команды.
* <span style="color:blue;">**US.PPUV.1.8.** Как пользователь ППУВ на платформе СРВИ, я хочу видеть все доступные локальные и региональные камеры в едином каталоге/карте СРВИ с фильтром по источнику, чтобы работать с федеративной системой из одного интерфейса.</span>

### 2.2. Скрытие архива

* **US.PPUV.2.1.** Как пользователь ППУВ на платформе СРВИ, я хочу скрывать выбранный интервал архива камеры (в том числе проекции региональной площадки) от гражданских пользователей, чтобы ограничить доступ к чувствительным записям без физического изъятия.
* **US.PPUV.2.2.** Как пользователь ППУВ на платформе СРВИ, я хочу дублировать фрагмент архива в защищённый контур СРВИ (RFM) без удаления с регионального Nimble, чтобы выбранный при блокировании фрагмент сохранился на длительный период времени.
* **US.PPUV.2.3.** Как пользователь ППУВ на платформе СРВИ, я хочу иметь возможность вернуть скрытый интервал архива, чтобы при ошибочном наложении блокировки была возможность исправить ошибку.
* **US.PPUV.2.4.** Как пользователь ППУВ на платформе СРВИ, я хочу заранее включить резервирование архива для федеративной камеры (параллельная запись на медиастример СРВИ без скрытия live от гражданских), чтобы при отказе региональной площадки сохранились live и свой архив в контуре СРВИ.
* <span style="color:blue;">Резервирование может быть задано на период или включено бессрочно до ручного снятия.</span>
* **US.PPUV.2.5.** Как пользователь ППУВ на платформе СРВИ, я хочу сохранить копию уже записанного исторического фрагмента архива (файл из Nimble региона) в RFM СРВИ без блокировки live и без удаления записи с регионального медиастримера, чтобы иметь долгосрочную копию в защищённом контуре, не лишая гражданских доступа к оригиналу.
* <span style="color:blue;">**US.PPUV.2.6.** Как пользователь ППУВ на платформе СРВИ, я хочу смотреть полный таймлайн федеративной камеры в плеере СРВИ, чтобы обычные участки подтягивались из регионального архива, а заблокированные/изъятые/зарезервированные — из источников СРВИ и RFM.</span>

### 2.3. Администрирование и журнал

* **US.PPUV.3.1.** Как пользователь ППУВ на платформе СРВИ, я хочу просматривать историю и текущие блокировки с фильтрами и управлять ими из единого журнала блокировок, чтобы контролировать жизненный цикл операций ППУВ.
* **US.PPUV.3.2.** Как пользователь ППУВ на платформе СРВИ, я хочу менять статус своих активных блокировок через журнал блокировок, чтобы точечно управлять процессом.
* **US.PPUV.3.3.** Как системный администратор, я хочу назначать ролям права ППУВ (приоритет управления, блокировка камеры, блокировка архива, перехват чужих блокировок) в Resource Management своей платформы, чтобы разграничить полномочия без изменения кода.
* **US.PPUV.3.4.** Как администратор системы, я хочу, чтобы при отсутствии лицензии PPUV весь связанный UI ППУВ был скрыт, чтобы пользователи не видели недоступный функционал.

### 2.4. Особенности работы платформы

* **US.PPUV.4.1.** Как пользователь ППУВ на платформе СРВИ, я хочу, чтобы мои действия не фиксировались в аудите региональной платформы при сохранении полной записи в аудите СРВИ, чтобы сохранять тайну операции для гражданского контура.
* **US.PPUV.4.2.** Как пользователь ППУВ на платформе СРВИ, я хочу видеть происхождение камеры (локальная СРВИ, регион A, регион B) и заблокированные интервалы на таймлайне, чтобы однозначно понимать источник данных при работе с федеративными камерами.
* <span style="color:blue;">**US.PPUV.4.3.** Как разработчик/администратор федерации, я хочу иметь явную настройку доверенных региональных контуров и их идентификаторов, чтобы RSM СРВИ не путал камеры разных регионов и корректно маршрутизировал S2S-команды.</span>

### UC-PPUV-01: Блокировка камеры

Пользователь накладывает фильтр по источнику.<br>4. Система отображает только камеры выбранного источника.<br>5. Пользователь выбирает одну из камер.<br>6. Пользователь нажимает на иконку замка.<br>11. Система проверяет его права:<br>&nbsp;&nbsp;11.1. Если это админ ППУВ или автор блокировки, переход на альтернативный сценарий 1.<br>&nbsp;&nbsp;11.2. Система открывает выбор пресета TTL.<br>14. Пользователь выбирает период и подтверждает.<br>15. Система отправляет `POST /gateway/rsm/locks` (`lockType=SPOOFING`).<br>16. RSM создаёт Spoofing-lease и **автоматически** сопутствующий Archive-lease (`coupledFromLeaseId`).<br>17. <span style="color:blue;">Для федеративной камеры RSM по `regionalInstallationId` отправляет команду в нужный региональный RSM; регион применяет логическое скрытие для гражданских, а СРВИ запускает собственную запись периода блокировки.</span><br>18. Гражданский: камера **исчезает** из раскладки с заменой на случайную онлайн-камеру, если feature flag включён, или в одиночном просмотре показывает "камера не работает"; архив и аналитика за период **скрыты**.<br>22. По событиям `LockExpired` / `LockRevoked` / `SpoofingStateChanged` UI обновляется без перезагрузки страницы.<br>23. ППУВ снимает блокировку или истекает TTL.<br>24. <span style="color:blue;">Система инициирует сохранение фрагмента блокировки в RFM СРВИ и связывает его с таймлайном камеры.</span> |

Система отправляет `DELETE /gateway/rsm/locks/{leaseId}` (или release по API).<br>2. RSM выполняет release; для федеративной — S2S "spoofing stop", восстановление live на регионе.<br>3. У гражданского пользователя live восстановлен; архив за период операции остаётся недоступен, если сохранена/действует архивная блокировка.<br>4. ### UC-PPUV-02: Перехват управления PTZ федеративной камеры

| **Наименование** | **UC-PPUV-02: Перехват управления PTZ федеративной камеры** |
| --- | --- |
| **Актор** | Пользователь ППУВ на платформе СРВИ |
| **Предусловия** | 1. Пользователь авторизован на **СРВИ**.<br>2. Гражданский оператор на **региональной платформе** управляет PTZ этой камеры.<br><span style="color:blue;">3. СРВИ знает регион-источник камеры и внешний идентификатор для S2S-команды.</span> |
| **Постусловия** | PTZ-управление у ППУВ на СРВИ; у гражданского на регионе джойстик отключён; live и архив доступны обоим. |
| **Основной сценарий** | 1. Спецпользователь на СРВИ открывает проекцию региональной PTZ-камеры.<br>2. Система отображает кнопку управления камерой.<br>3. Пользователь нажимает кнопку.<br>4. Система отправляет `POST /gateway/rsm/locks` (`lockType=PTZ`, `resourceId`).<br>5. RSM СРВИ определяет `externalId` и `regionalInstallationId`.<br>6. RSM сравнивает приоритеты и выполняет preemption.<br>7. RSM СРВИ отправляет S2S-команду в RSM региона: сброс PTZ-сессии гражданского оператора.<br>8. DCS региона сбрасывает сессию; UI региона показывает уведомление гражданскому.<br>9. RSM СРВИ создаёт PTZ-lease; публикует `LockGranted` в Kafka.<br>10. Система активирует джойстик ППУВ на СРВИ.<br>11. Запись в Audit **СРВИ**; в Audit региона — **нет** следа операции ППУВ. |
| **Альтернативный сценарий 1. Равный приоритет** | 1. На шаге 6 RSM видит, что камера занята пользователем с **равным** `ppuv_priority`.<br>2. RSM возвращает `REJECTED` / `409 RESOURCE_BUSY`.<br>3. Система показывает сообщение: ресурс занят; джойстик не активируется. |
| **Исключающий сценарий 1. Ошибка S2S** | 1. На шаге 7 регион не отвечает или возвращает ошибку.<br>2. RSM СРВИ не подтверждает lease (статус "Ошибка").<br>3. Система показывает ошибку оператору; PTZ у гражданского может остаться активным до повторной попытки. |

### UC-PPUV-03: Массовая блокировка камер на карте (лассо)

|  |  |
| --- | --- |
| **Наименование** | **UC-PPUV-03: Массовая блокировка камер на карте (лассо)** |
| **Актор** | Пользователь ППУВ на платформе СРВИ |
| **Предусловия** | 1. Пользователь авторизован на СРВИ.<br>2. На карте отображены камеры с координатами (локальные и проекции регионов). |
| **Постусловия** | Успешно заблокированные камеры отмечены иконкой замка; в журнале СРВИ — записи lease; для федеративных — применены S2S-команды в регионы. |
| **Основной сценарий** | 1. Спецпользователь на карте СРВИ рисует полигон.<br>2. Спецпользователь нажимает **"Заблокировать выбранные"**.<br>3. Система открывает модальное окно с пресетами TTL.<br>4. Пользователь выбирает период и подтверждает.<br>5. Система определяет количество камер:<br>&nbsp;&nbsp;5.1. Если камер ≤ 50, система отправляет `POST /gateway/rsm/locks/batch` (SPOOFING).<br>&nbsp;&nbsp;5.2. Если камер > 50, система выводит сообщение: "Достигнут лимит в 50 камер для блокировки. Уменьшите количество и повторите операцию".<br>6. RSM обрабатывает **покамерно**: acquire / reject / preempt.<br>7. Для федеративных камер RSM отправляет S2S в соответствующие регионы.<br>8. Система показывает сводку: "Заблокировано N, отклонено M, вытеснено K".<br>9. Система вносит данные в аудит на платформе СРВИ.<br>10. Блокировка каждой отдельной камеры происходит аналогично UC-PPUV-01. |
| **Альтернативный сценарий 1. Массовая разблокировка** | 1. Спецпользователь выделяет на карте область или выбирает записи в журнале блокировок.<br>2. Спецпользователь нажимает **"Снять блокировку"**.<br>3. Система формирует список `leaseId`:<br>&nbsp;&nbsp;3.1. Если пользователь без прав `admin:ppuv`, определяется перечень камер, где пользователь — владелец блокировки.<br>&nbsp;&nbsp;3.2. Если пользователь с правом `admin:ppuv`, используется полный перечень камер.<br>4. Система отправляет `POST /gateway/rsm/locks/batch/release`.<br>5. RSM снимает lock покамерно; для федеративных — S2S "spoofing stop" в регион.<br>6. Система показывает "Снято N из M" (partial success при чужих lock в области). |

### UC-PPUV-04: Логическая блокировка архива

|  |  |
| --- | --- |
| **Наименование** | **UC-PPUV-04: Логическая блокировка архива (без изъятия)** |
| **Актор** | Пользователь ППУВ на платформе СРВИ |
| **Предусловия** | 1. Пользователь авторизован на СРВИ с правом блокировки архива.<br>2. На таймлайне есть записи за выбранный интервал.<br><span style="color:blue;">3. Для федеративной камеры СРВИ может получить региональные DVR/HLS-сегменты или инициировать выгрузку файла через S2S.</span> |
| **Постусловия** | У гражданских — дыра на таймлайне; у ППУВ — полный доступ; при снятии lock доступ гражданским **восстанавливается**. |
| **Основной сценарий** | 1. ППУВ открывает таймлайн камеры (локальной или проекции региона) на СРВИ.<br>2. Пользователь выделяет интервал `[startTime, endTime]`.<br>3. Система предлагает варианты:<br>&nbsp;&nbsp;- Скрыть архив<br>&nbsp;&nbsp;- Изъять архив<br>&nbsp;&nbsp;- Сохранить копию<br>4. Пользователь выбирает **"Скрыть архив"**.<br>5. Система отправляет `POST /gateway/rsm/locks` (`lockType=ARCHIVE`).<br>6. RSM создаёт Archive-lease; для федеративной камеры — S2S в регион.<br>7. MSS региона помечает интервал как `BlockedArchive` для гражданских.<br>8. Гражданский на регионе видит **дыру** на таймлайне; live **не затронут**.<br>9. <span style="color:blue;">События аналитики и нотификации региона за интервал также скрываются от гражданского пользователя региона.</span><br>10. ППУВ видит архив полностью и границы скрытого интервала в плеере СРВИ.<br>11. ППУВ снимает блокировку из таймлайна или журнала.<br>12. Доступ гражданских к архиву **восстанавливается**. |
| **Альтернативный сценарий 1. Дублирование в спецархив** | После п. 3 основного сценария.<br>1. Пользователь нажимает **"Дублирование в спецархив"** / **"Изъять архив"**.<br>2. Система отправляет в RSM запрос Archive-lock и команду извлечения.<br>3. RSM СРВИ через S2S инициирует `ExtractArchiveToStorage` на регионе.<br>4. MSS региона выгружает файл с Nimble/медиастримера (не "перенос потока").<br>5. Файл загружается в **RFM СРВИ**.<br>6. Гражданский видит пустой/заблокированный интервал на таймлайне региона.<br>7. ППУВ видит копию в RFM и метку на таймлайне СРВИ.<br>8. Система вносит данные в аудит на платформе СРВИ. |
| **Альтернативный сценарий 2. Сохранить копию архива** | 1. Пользователь выбирает **"Сохранить копию"** без скрытия интервала.<br>2. Система через S2S получает файл из регионального архива и сохраняет его в RFM СРВИ.<br>3. Оригинальный архив и live региона остаются доступными гражданским пользователям.<br>4. <span style="color:blue;">Копия отображается в СРВИ как RFM-фрагмент, доступный из таймлайна камеры или из раздела сохранённых записей.</span> |
| **Исключающий сценарий 1. Пересечение архивов** | 1. Выделенный интервал частично пересекается с ранее скрытым / изъятым фрагментом.<br>2. Система блокирует операцию и показывает: "Нельзя выделить пересекающийся интервал". |

### UC-PPUV-09: Скрытность операций ППУВ в аудите (федерация)

|  |  |
| --- | --- |
| **Наименование** | **UC-PPUV-09: Скрытность операций ППУВ в аудите федерации** |
| **Актор** | Пользователь ППУВ на СРВИ; администратор региональной платформы |
| **Связанные US** | US.PPUV.4.1 |
| **Предусловия** | 1. ППУВ выполняет операцию над федеративной камерой (блокировка, PTZ, архив, <span style="color:blue;">резервирование или выборочная запись</span>). |
| **Постусловия** | Audit СРВИ содержит полную запись; Audit региона — **не содержит** следов ППУВ. |
| **Основной сценарий** | 1. ППУВ на СРВИ выполняет операцию над федеративной камерой.<br>2. RSM СРВИ фиксирует операцию в Audit **СРВИ**.<br>3. RSM СРВИ отправляет S2S в регион **без** пользовательского контекста ППУВ в гражданском аудите.<br>4. Гражданский оператор региона продолжает работу; в своём Audit **не находит** записей о блокировке/изъятии/резервировании.<br>5. Администратор СРВИ в Audit СРВИ **видит** полную цепочку действий ППУВ.<br>6. Администратор региона в Audit региона **не обнаруживает** операцию. |
