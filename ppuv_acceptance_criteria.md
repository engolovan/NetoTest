# Критерии приемки ППУВ

Актуализировано по документации по федеративной подсистеме приоритетного управления видеонаблюдением.

## 1. Федеративный каталог камер и фильтры

### Backend

* [ ] СРВИ хранит локальный слепок федеративных камер с собственным `resourceId`/`deviceId`, `externalId`, идентификатором регионального контура (`regionalInstallationId` или `externalSystemId`), названием, координатами, источником (`sourceName`) и ключевыми атрибутами для фильтрации.
* [ ] Изменения названия, координат, доступности и ключевых атрибутов камеры во внешней региональной системе синхронизируются в слепок СРВИ без ручного пересоздания камеры.
* [ ] Backend предоставляет данные для фильтрации по источнику камеры: локальная СРВИ, регион A, регион B и т.д.
* [ ] Backend предоставляет данные для фильтрации по активной блокировке камеры и может использовать этот признак совместно с существующими фильтрами карты/списка.
* [ ] Теги, иерархии и названия из разных источников не конфликтуют по одинаковым именам; при фильтрации учитывается источник/namespace.
* [ ] Если у источника нет собственной иерархии, backend отдает данные так, чтобы камеры могли быть показаны в корневом узле этого источника.
* [ ] При исчезновении камеры из регионального ответа backend переводит проекцию в согласованный статус деактивации/недоступности, не теряя связи с журналом блокировок и архивными фрагментами в RFM.
* [ ] RSM использует связь `resourceId` -> `externalId` + региональный контур для маршрутизации S2S-команд в правильную региональную платформу.

### Frontend

* [ ] Пользователь СРВИ видит локальные и федеративные камеры в общем каталоге, списке и на карте с понятным признаком источника.
* [ ] Фильтры источника и блокировки доступны на карте, в списке и в раскладках и не требуют перехода в региональную платформу.
* [ ] Если источник не имеет иерархии, камеры отображаются в корневом узле источника, а не теряются из каталога.
* [ ] На карте статус блокировки отображается только на одиночных камерах, которые реально присутствуют в ответе карты; кластеры не получают агрегированный замок.
* [ ] После раскрытия кластера или появления одиночной камеры интерфейс запрашивает/обновляет статус блокировки и показывает замок на конкретной камере.
* [ ] Finder/поиск и стандартные фильтры не ломаются при появлении новых полей источника и статуса блокировки.

## 2. Блокировка единичной камеры / потока

### Backend

* [ ] Сформирована возможность создать блокировку потока для одной камеры с проверкой лицензии PPUV, прав пользователя, доступности камеры и максимального TTL; дефолтный максимум TTL - 3 дня.
* [ ] Максимальный TTL отдается фронту через сервис/конфигурацию блокировок, а backend повторно валидирует TTL и возвращает понятную ошибку при превышении.
* [ ] При успешной блокировке потока создается lease блокировки камеры и связанная блокировка архива за период спецрежима.
* [ ] Блокировка камеры решается покамерно; конфликт по одной камере не блокирует автоматически всю зону или группу.
* [ ] Если на камере активен PTZ-lease, включение блокировки потока вытесняет/завершает существующее PTZ-управление, потому что блокировка потока приоритетнее PTZ-lock.
* [ ] На региональной платформе применяется логическое скрытие live/архива для гражданского контура; данные на региональной платформе не удаляются.
* [ ] Одновременно СРВИ включает собственную запись/копию нужного потока на своем медиастримере на период блокировки.
* [ ] После завершения блокировки фрагмент за период блокировки фиксируется в RFM СРВИ для долговременного хранения согласно политике хранения.
* [ ] По истечении TTL или ручном снятии блокировки публикуется событие изменения состояния, статус lease обновляется, параллельная запись останавливается.
* [ ] Гражданский пользователь региона не видит live во время активной блокировки, а архив, события аналитики и нотификации за период блокировки остаются недоступны и после снятия блокировки потока.
* [ ] Audit СРВИ фиксирует успешные и неуспешные попытки блокировки; гражданский Audit региона не содержит следов ППУВ.

### Frontend

* [ ] Пользователь ППУВ может открыть карточку/плеер единичной камеры и запустить блокировку потока с выбором длительности.
* [ ] UI выбора длительности не позволяет указать значение больше максимума из конфигурации; пользователь видит понятное ограничение.
* [ ] После установки блокировки камера отображается с явным состоянием блокировки: замок, подпись/статус и таймер.
* [ ] После установки блокировки потока действие "Блокировка PTZ" для этой камеры недоступно и сопровождается пояснением, что управление уже заблокировано из-за блокировки потока.
* [ ] Пользователь СРВИ видит реальный live-поток, запись и заблокированный интервал на таймлайне камеры.
* [ ] Гражданский пользователь в одиночном просмотре видит состояние "камера не работает" или эквивалентную заглушку.
* [ ] Гражданский пользователь в раскладке видит подмену заблокированной камеры только если включен соответствующий feature flag; по умолчанию feature flag выключен.
* [ ] Статус блокировки, таймер и доступность действий обновляются в интерфейсе по событиям без перезагрузки страницы.

## 3. Блокировка PTZ единичной камеры

### Backend

* [ ] Сформирована возможность создать отдельный PTZ-lease для одной PTZ-камеры без скрытия live и архива.
* [ ] При создании PTZ-блокировки система проверяет лицензию PPUV, права, приоритет пользователя, доступность PTZ и максимальный TTL; дефолтный максимум TTL - 3 дня.
* [ ] Если PTZ уже занят пользователем с меньшим приоритетом, текущая PTZ-сессия сбрасывается через S2S/DCS, а новый PTZ-lease создается для пользователя ППУВ.
* [ ] Если PTZ занят пользователем с равным или более высоким приоритетом, применяется правило первого занявшего: API возвращает конфликт (`409 RESOURCE_BUSY` или эквивалент) и не создает новый lease.
* [ ] Если PTZ-lease активен, а затем включается блокировка потока, текущая PTZ-сессия сбрасывается, предыдущий PTZ-lease переводится в завершенное/вытесненное состояние, а управление PTZ доступно только автору блокировки потока.
* [ ] При снятии или истечении PTZ-lease live и архив остаются без изменений, а доступность управления пересчитывается по текущим ограничениям.
* [ ] Предыдущий оператор получает уведомление при перехвате PTZ или вытеснении PTZ блокировкой потока.

### Frontend

* [ ] Пользователь может поставить PTZ-блокировку на единичную камеру с выбором длительности в пределах конфигурационного лимита.
* [ ] При активной PTZ-блокировке live и архив остаются доступны, а управление PTZ для других пользователей отключено.
* [ ] Пользователь может увидеть статус PTZ-блокировки, свою принадлежность и оставшееся время.
* [ ] При конфликте приоритетов интерфейс показывает понятное сообщение, что ресурс занят.
* [ ] При перехвате PTZ гражданский пользователь региона видит отключение управления и уведомление о перехвате пользователем с большим приоритетом.
* [ ] При PTZ-lock без перехвата live, архив, события и нотификации для гражданского пользователя остаются доступны; панель управления скрыта/заблокирована без раскрытия деталей ППУВ.
* [ ] При истечении или снятии PTZ-блокировки UI обновляет доступность управления без перезагрузки страницы.

## 4. Массовая блокировка камер по области на карте

### Backend

* [ ] Сформирована возможность принять геометрию области, тип массовой операции и TTL, а затем определить на сервере список камер, попавших в область, включая камеры внутри кластеров.
* [ ] Массовая операция поддерживает блокировку потока и блокировку PTZ. Резервирование архива не выбирается в сценарии массовой блокировки по лассо.
* [ ] Сервер проверяет лимит количества камер для массовой операции; при превышении лимита операция не запускается. Дефолтный лимит - 50 камер.
* [ ] RSM обрабатывает массовую операцию покамерно: acquire / reject / preempt.
* [ ] Для федеративных камер RSM отправляет S2S-команды в соответствующие регионы на основании источника камеры.
* [ ] Результат массовой операции возвращает partial success: сколько камер заблокировано, сколько отклонено, сколько вытеснено.
* [ ] Массовое снятие блокировок принимает список `leaseId` или область, пересчитывает доступные пользователю блокировки и снимает только те lease, на которые у пользователя есть права.
* [ ] Массовое продление блокировок не поддерживается; продление возможно только точечно для одной выбранной активной блокировки.

### Frontend

* [ ] Пользователь может выделить область на карте и выбрать тип массовой операции: блокировка потока или блокировка PTZ, а также длительность.
* [ ] Фронт отправляет на backend геометрию области, тип операции и TTL, а не требует от пользователя раскрывать кластеры и перечислять `cameraId`.
* [ ] После выполнения операции пользователь видит сводку результата: заблокировано, отклонено, вытеснено.
* [ ] Если лимит камер превышен, интерфейс показывает понятное сообщение и предлагает уменьшить область.
* [ ] Индикатор блокировки на карте отображается только на одиночных камерах; кластеры не получают агрегированный замок.
* [ ] После раскрытия кластера или появления одиночной камеры интерфейс обновляет статус блокировки и показывает замок на конкретной камере.
* [ ] В сценарии массового снятия пользователь видит итог: сколько блокировок снято и сколько отклонено.
* [ ] Интерфейс не предлагает массовое продление блокировок.

## 5. Журнал блокировок

### Backend

* [ ] Сформирован API журнала блокировок, который возвращает не только id, но и читабельные данные: камера, источник, тип, статус, владелец, время начала, время окончания, кто снял.
* [ ] Журнал хранит текущие и исторические состояния lease; одна блокировка отображается одной строкой со статусом и жизненным циклом, а продление обновляет время окончания активной строки, не создавая новую строку.
* [ ] Для блокировки потока связанная блокировка архива доступна как связанное состояние/атрибут операции, чтобы пользователь не видел дублирующие несогласованные строки.
* [ ] Backend поддерживает снятие активной блокировки с проверкой прав владельца или администратора ППУВ (`ppuv:admin`).
* [ ] Backend поддерживает точечное продление одной активной блокировки с проверкой прав, статуса lease и максимального TTL.
* [ ] Backend не поддерживает массовое продление блокировок.
* [ ] Журнал поддерживает фильтрацию/пагинацию по статусу, типу, камере, источнику, инициатору и датам.
* [ ] При снятии чужой блокировки администратором ППУВ владелец получает уведомление, а в журнале фиксируется, кто снял блокировку.

### Frontend

* [ ] Пользователь может открыть журнал блокировок и увидеть список текущих и исторических блокировок с читабельными названиями камер и источников.
* [ ] В журнале доступны фильтры по статусу, типу, инициатору, камере, источнику, датам и режим "только активные".
* [ ] Для активных блокировок доступны действия "Снять" и "Продлить" с учетом прав пользователя.
* [ ] Действие "Продлить" доступно только при выборе одной активной блокировки.
* [ ] После продления в журнале обновляется время окончания той же строки блокировки.
* [ ] Чекбоксы и действия для завершенных блокировок неактивны.
* [ ] Журнал позволяет удобно работать с массовыми блокировками, когда повторно выделить ту же область на карте сложно.
* [ ] Пользователь видит сводку снятия блокировок: сколько снято, сколько отклонено.

## 6. Архив, RFM и резервирование камеры

### Backend

* [ ] При блокировке потока период блокировки записывается/сохраняется в контуре СРВИ и после завершения попадает в RFM согласно политике хранения.
* [ ] Nimble/медиастример не используется как надежное долговременное хранилище для фрагментов спецоперации; после завершения блокировки запускается системный процесс сохранения фрагмента в RFM.
* [ ] Сформирована возможность логически заблокировать выбранный интервал архива без скрытия live. Такая блокировка обратима и не снимается автоматически по TTL.
* [ ] При логической блокировке архива гражданский пользователь региона не видит архивные сегменты, события аналитики и нотификации за соответствующий интервал.
* [ ] Сформирована возможность физической блокировки выбранного фрагмента: система накладывает логическую блокировку для гражданского контура и сохраняет копию фрагмента в RFM СРВИ.
* [ ] Сформирована возможность сохранить фрагмент архива в RFM на контуре СРВИ без удаления оригинала с регионального Nimble.
* [ ] Если сохраняемый исторический фрагмент уже целиком есть в резерве/RFM, система сообщает об этом пользователю и не создает дубль без явного подтверждения.
* [ ] Сформирована возможность включить резервирование федеративной камеры: параллельную запись на медиастример СРВИ без скрытия live, архива, событий и нотификаций от гражданского контура.
* [ ] Уже записанные в резерве фрагменты остаются доступны в СРВИ согласно политике хранения после снятия Reserve-lease.
* [ ] Зарезервированный архив виден всем пользователям СРВИ, которым доступна соответствующая камера/запись, чтобы не создавать двойную запись для разных пользователей.
* [ ] Плеер СРВИ получает данные для единого таймлайна федеративной камеры из регионального медиастримера, стримера СРВИ и RFM.
* [ ] При отсутствии регионального архива за период, но наличии сохраненного фрагмента в RFM/резерве СРВИ, backend отдает этот фрагмент для таймлайна камеры.
* [ ] При конфликте нескольких сохраненных копий одного периода для таймлайна выбирается последняя по дате создания, если не задано иное правило.
* [ ] Операции архива, RFM и резервирования пишутся в Audit СРВИ и не появляются в гражданском Audit региона.

### Frontend

* [ ] Оператор СРВИ видит архив федеративной камеры как единый таймлайн, даже если физически интервалы лежат в регионе, на стримере СРВИ и в RFM.
* [ ] Заблокированные фрагменты имеют понятные отметки на таймлайне камеры.
* [ ] Пользователь может инициировать логическую блокировку выбранного интервала архива из таймлайна СРВИ.
* [ ] Пользователь может снять логическую блокировку архива, если является владельцем или имеет `ppuv:admin`; при выборе нескольких блокировок видит подтверждение и итог частичного снятия.
* [ ] Пользователь ППУВ может экспортировать/скачать заблокированный архивный интервал из СРВИ при наличии прав; гражданскому пользователю региона экспорт этого интервала недоступен.
* [ ] Пользователь может инициировать сохранение исторического фрагмента в RFM из таймлайна СРВИ без блокировки live и без удаления оригинала у региона.
* [ ] Пользователь может включить и снять резервирование федеративной камеры.
* [ ] Управление резервированием не размещается третьей строкой в модальном окне блокировки потока/PTZ; используется отдельный элемент управления в карточке/плеере после UX-решения.
* [ ] При резервировании без блокировки гражданский пользователь региона продолжает видеть live, архив, события и нотификации без изменений.
* [ ] Пользователь СРВИ не видит события аналитики и нотификации региональной платформы по федеративной камере; аналитика регионов не агрегируется в СРВИ.

## 7. Аудит, события и скрытность операций ППУВ

### Backend

* [ ] Все успешные и неуспешные операции ППУВ над локальными и федеративными камерами пишутся в Audit СРВИ.
* [ ] S2S-команды в регион выполняются без пользовательского контекста ППУВ в гражданском аудите и не создают видимые записи о ППУВ-операциях в Audit региона.
* [ ] Региональная платформа скрывает от гражданских пользователей архивные сегменты, события аналитики и нотификации за интервал блокировки потока или архива.
* [ ] Пользователь СРВИ не получает доступ к Audit региональной платформы через сценарии ППУВ.

### Frontend

* [ ] В UI СРВИ отображаются статусы блокировок, таймеры и доступность действий по событиям без перезагрузки страницы.
* [ ] Региональный гражданский пользователь не видит в интерфейсе и аудите, что ограничения вызваны действиями спецпользователя СРВИ.
* [ ] При установке блокировки архива во время просмотра событий/нотификаций гражданским пользователем список обновляется без перезагрузки, скрытые элементы исчезают, а пользователь видит нейтральное уведомление о недоступности данных.

## 8. Доступность ППУВ по лицензии и правам

### Backend

* [ ] Операции ППУВ недоступны без активной лицензии PPUV и соответствующих прав; при отказе не создаются lease и не запускаются S2S-команды.
* [ ] В федеративной схеме лицензия PPUV активна на обеих платформах: на СРВИ для UI и инициирования операций, на регионе для исполнения доверенных S2S-команд.
* [ ] Лицензия PPUV является булевой и не ограничивает количество камер, пользователей, региональных проекций или операций.
* [ ] Региональная платформа не предоставляет пользовательский UI ППУВ и не дает региональным пользователям операторские функции ППУВ.
* [ ] Права ППУВ на контуре СРВИ включают минимум: блокировка камеры, перехват PTZ, блокировка архива, PTZ-lock, резервирование, администрирование ППУВ.
* [ ] Любое право ППУВ дает пользователю возможность просматривать журнал блокировок.
* [ ] Права владельца блокировки и администратора ППУВ учитываются при снятии и продлении блокировок.
* [ ] Снять блокировку может только владелец или пользователь с правом `ppuv:admin`.

### Frontend

* [ ] При отсутствии лицензии или прав UI ППУВ скрыт.
* [ ] Пользователь без прав не может снять или продлить чужую блокировку; доступные действия соответствуют данным правам.
* [ ] Пользователь с правами `ppuv:admin` может снять блокировку другого пользователя.
* [ ] Пользователь с любым правом ППУВ может открыть журнал блокировок.
* [ ] Пользователь региональной платформы не видит операторские элементы ППУВ даже при активной региональной лицензии PPUV.

## 9. Интеграционные API и ответы операций

### Backend

* [ ] Интеграция между СРВИ и региональными платформами выполняется через RSM/S2S API, а не через склейку внутренних сервисов разных инсталляций.
* [ ] S2S API защищены типовыми механизмами межсистемной интеграции: доверенный контур СРВИ, ключи/client id, проверка подписи и разграничение по приоритетам.
* [ ] API блокировок использует acquire/release endpoints, пригодные для будущего сервиса расписаний без отдельной логики внутри RSM.
* [ ] Операции блокировки возвращают однозначные состояния: успешно установлено, ошибка не установлена, вытеснено/снято другим пользователем или более приоритетной операцией.
* [ ] При ошибке S2S lease переводится в статус "Ошибка", пользователь получает сообщение, гражданский контур не меняется, Audit СРВИ фиксирует неуспешную попытку.

### Frontend

* [ ] Пользователь видит понятные сообщения для успешной операции, системной ошибки, конфликта занятости ресурса и вытеснения блокировки.
* [ ] При частичном успехе массовых операций интерфейс показывает агрегированную сводку и позволяет понять, какие камеры не были обработаны.
